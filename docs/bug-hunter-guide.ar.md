هذا الدليل مكتوب لمن سيطور المهارة ويصونها، وليس لمن سيستخدمها فقط. الهدف أن تفهم كل قرار فيها: لماذا الملف هنا، ولماذا الجملة مكتوبة بهذه الطريقة، وكيف تثبت أن أي تعديل جعلها أفضل فعلا.

## 1. الفكرة في دقيقة

وكيل البرمجة (Coding Agent) مثل Claude Code أو Codex أو Cursor يكتب ميزة كاملة في دقائق. المشكلة أنه يحسن لهدف واحد: أن تعمل الميزة. أما سؤال "ماذا لو استخدمها شخص بطريقة لم يتوقعها أحد؟" فلا يطرحه إلا إذا طلبت منه.

المهارة bug-hunter تجعله يطرح هذا السؤال وحده، في اللحظة المناسبة، وبالقدر المناسب. عندما يبني ميزة حساسة يكتب أولا قائمة هجمات واقعية على هذه الميزة بالذات، ثم يبنيها بحيث تغلق هذه الهجمات، ثم يهاجم الكود الذي كتبه، ثم يثبت الحماية باختبارات، ثم يكتب تقريرا قصيرا صادقا. وعندما تكون المهمة تغيير لون زر لا يفعل أي شيء من هذا.

## 2. ما هي الـ Agent Skill بالضبط؟

المهارة مجلد. داخله ملف إلزامي واحد اسمه `SKILL.md`، ويمكن أن يضم مجلدات اختيارية:

```text
bug-hunter/
├── SKILL.md          # إلزامي: بيانات وصفية + التعليمات الأساسية
├── references/       # معرفة تفصيلية تقرأ عند الحاجة فقط
├── scripts/          # كود ينفذه الوكيل ولا يقرؤه
└── assets/           # قوالب وملفات تستخدم في المخرجات (لا نحتاجه هنا)
```

يبدأ الملف `SKILL.md` بكتلة YAML بين سطرين من الشرطات، ثم يأتي نص Markdown عادي:

```markdown
---
name: bug-hunter
description: Builds and changes code the way a bug bounty hunter would attack it...
license: MIT
metadata:
  author: Flint
  homepage: https://flint.ps
  version: "0.1.0"
---

# Bug Hunter
...التعليمات...
```

### قواعد الحقول

حسب مواصفة Agent Skills المفتوحة:

| الحقل | القاعدة |
|---|---|
| `name` | من 1 إلى 64 حرفا، أحرف إنجليزية صغيرة وأرقام وشرطات فقط، لا يبدأ ولا ينتهي بشرطة، بلا شرطتين متتاليتين، ويطابق اسم المجلد |
| `description` | من 1 إلى 1024 حرفا، يشرح ماذا تفعل المهارة ومتى تستخدم |
| `license` | اختياري |
| `compatibility` | اختياري، حتى 500 حرف، للمتطلبات الخاصة |
| `metadata` | اختياري، أزواج مفتاح وقيمة نصية |
| `allowed-tools` | اختياري وتجريبي، قائمة أدوات مفصولة بمسافات |

وبعض المنصات ترفض كلمات محجوزة في الاسم مثل `claude` و`anthropic`، وترفض وسوم XML داخل الوصف.

### الكشف التدريجي (Progressive Disclosure)

هذا هو المبدأ الأهم في الموضوع كله. تخيل مكتبة: على الرف ترى عنوان كل كتاب فقط. تسحب الكتاب الذي يناسب سؤالك وتقرأ فهرسه وفصله الأول. ثم تفتح الملحق المحدد الذي تحتاجه، ولا تقرأ الملاحق الأخرى.

الوكيل يتعامل مع المهارات بالطريقة نفسها، على ثلاث طبقات:

| الطبقة | ماذا يحمل | متى | التكلفة التقريبية |
|---|---|---|---|
| 1 | الاسم والوصف لكل مهارة مثبتة | دائما، في كل محادثة | نحو 100 token لكل مهارة |
| 2 | نص `SKILL.md` | عندما يقرر الوكيل أن المهارة تناسب المهمة | يفضل أقل من 5000 token وأقل من 500 سطر |
| 3 | ملفات `references/` و`scripts/` | عندما تطلبها التعليمات أو تحتاجها المهمة | حسب الملف، والسكربت لا يدخل السياق أصلا، فقط ناتجه |

في bug-hunter الحالية: الوصف نحو 735 حرفا، ونص `SKILL.md` نحو 2000 token، وكل ملف مرجعي بين 500 و950 كلمة. المهمة التي تخص webhook تقرأ ملف الـ webhooks وملف إطار العمل فقط.

لماذا يهم هذا؟ لأن نافذة السياق (Context Window) ميزانية مشتركة. كل token تضعه فيها يكلف مالا، ويأخذ من انتباه النموذج. التعليمات المدفونة وسط نص طويل تضعف. لذلك المهارة الجيدة قصيرة في المركز، عميقة في الأطراف.

### الفرق بين المهارة والـ prompt والـ MCP

| الأداة | ما هي | متى تناسب |
|---|---|---|
| prompt أو ملف `CLAUDE.md` | نص يحمل في كل مرة | قواعد المشروع التي تنطبق دائما |
| Skill | معرفة وإجراءات تحمل عند الحاجة فقط | خبرة متخصصة لا تحتاجها كل مهمة |
| MCP Server | أدوات تتصل بأنظمة خارجية | قراءة وكتابة بيانات في تطبيقات أخرى |

المعرفة الأمنية مثال مثالي على المهارة: تحتاجها بعمق في بعض المهام، ولا تحتاجها أبدا في مهام أخرى.

## 3. كيف يقرر الوكيل تحميل المهارة؟

لا يوجد سحر ولا بحث دلالي معقد في أغلب الوكلاء. النموذج يقرأ قائمة الأسماء والأوصاف مع طلب المستخدم، ويقرر بنفسه. لذلك الوصف هو الموجه (Router) الوحيد. إن كان ضعيفا فالمهارة لن تعمل مهما كانت تعليماتها ممتازة.

### مشكلة قلة التفعيل

النماذج الحالية تميل إلى عدم تحميل المهارات حتى عندما تفيد. المستخدم يكتب "أضف endpoint لرفع الصور" ولا يذكر كلمة أمن، فلا يربط النموذج الطلب بمهارة أمنية. الحل الذي توصي به أدلة كتابة المهارات أن يكون الوصف "ملحا" قليلا: يذكر المواقف صراحة، ويقول إنها تنطبق حتى لو لم يذكر المستخدم الأمن.

### تشريح وصف bug-hunter

| الجزء | وظيفته |
|---|---|
| Builds and changes code the way a bug bounty hunter would attack it | ماذا تفعل، بجملة واحدة |
| authentication, authorization, sessions, payments... | الأسطح الحساسة، وهي الكلمات التي سيطابقها النموذج |
| maps the attack surface, writes concrete abuse cases... | كيف تعمل، ليفهم النموذج أنها تغير طريقة البناء وليست مراجعة لاحقة |
| Use this skill whenever the user asks to build, change, review... | متى تستخدم، بأفعال يستخدمها الناس فعلا |
| even if they never mention security | علاج قلة التفعيل |
| Skip it for styling, copy, documentation-only... | متى لا تستخدم، لمنع التفعيل الزائد |

الوصف مكتوب بصيغة الغائب (Builds) وليس "I build" أو "You build"، لأن الوصف يدخل في الـ system prompt ويجب أن يقرأ كوصف لأداة.

### اختبار التفعيل

قبل أي إصدار اكتب 20 طلبا يجب أن تحمل المهارة، و20 طلبا يجب ألا تحملها، وشغلها وعد النتائج. أمثلة:

| يجب أن تحمل | يجب ألا تحمل |
|---|---|
| Add a forgot password flow | Make the navbar sticky |
| Let users upload a profile picture | Fix the typo in the pricing page |
| Connect our Shopify webhooks | Convert this component to TypeScript |
| Add an admin page to ban users | Add dark mode |
| Build a chatbot that can cancel orders | Write unit tests for the date formatter |

الهدف أعلى من 90 بالمئة في الجهتين. إذا فشل التفعيل فعدل الوصف وليس النص.

## 4. رحلة طلب واحد من أوله إلى آخره

المستخدم يكتب: "Add a route so a logged-in user can download the PDF of one of their invoices". هذا ما يحدث:

```text
user prompt
   |
   v
[1] agent sees name + description of every installed skill
   |    match: route, logged-in, download -> bug-hunter
   v
[2] agent reads SKILL.md (~2k tokens)
   |    level 2: object access + files
   v
[3] map the surface: assets=invoice PDFs, actors=customer, other customer, guest
   |
   v
[4] abuse cases: B changes the ID / guest guesses URL / direct /storage access
   |
   v
[5] reads references/access-control.md, files.md, frameworks/laravel.md
   |
   v
[6] builds: query through $request->user(), private disk, auth group
   |
   v
[7] self-attack + tests: user B gets 404, guest redirected
   |
   v
[8] runs triage_diff.py --git to confirm no surface was missed
   |
   v
[9] security notes table at the end of the answer
```

لاحظ ثلاثة أشياء. الأول: الهجمات تكتب قبل الكود، فتوجه التصميم بدل أن تكتشف الأخطاء بعده. الثاني: الوكيل يقرأ ثلاثة ملفات مرجعية فقط من أصل خمسة عشر. الثالث: كل حماية تنتهي باختبار، والتقرير يشير إلى اسم الاختبار.

## 5. عقلية صائد الثغرات في سبعة أسئلة

هذا هو جوهر المهارة. كل ما فيها ترجمة لهذه الأسئلة إلى تعليمات يفهمها نموذج.

### السؤال الأول: من يتحكم بهذه القيمة؟

كل قيمة تصل إلى الكود لها مصدر. رقم في الرابط، حقل في JSON، header، cookie، ملف مرفوع، payload من webhook، صفحة ويب يقرؤها نموذج لغوي، وحتى قيمة في قاعدة البيانات كتبها مستخدم آخر. حدود الثقة (Trust Boundaries) هي النقاط التي تنتقل فيها البيانات من طرف أقل ثقة إلى طرف أعلى. معظم الثغرات تحدث عند هذه الحدود.

في المهارة: الخطوة الأولى في `SKILL.md` وملف `references/threat-model.md`.

### السؤال الثاني: إلى أين تذهب؟

فكر في كل قيمة كأنها ماء ملون يدخل من المصدر (Source) ويجري حتى المصب (Sink). المصب هو المكان الذي تصبح فيه القيمة خطيرة:

| المصب | الخطر |
|---|---|
| استعلام SQL أو NoSQL | حقن |
| نظام الملفات | Path Traversal |
| طلب HTTP يرسله الخادم | SSRF |
| HTML أو قالب | XSS أو SSTI |
| أمر shell | تنفيذ أوامر |
| redirect | Open Redirect |
| سياق نموذج لغوي أو أدواته | Prompt Injection |

في المهارة: قسم "Questions by sink" في `references/self-attack.md`.

### السؤال الثالث: ماذا لو كان الرقم لشخص آخر؟

أشهر ثغرة في برامج مكافآت الثغرات وأكثرها تكرارا. اسمها IDOR أو BOLA. الـ route محمي بتسجيل الدخول، لكن لا شيء يتحقق أن الفاتورة رقم 1044 تخص المستخدم الحالي. هذا هو السبب في أن Broken Access Control هو البند الأول في OWASP Top 10:2025.

القاعدة: لا تجلب الكائن ثم تتحقق من مالكه. اجلبه من خلال مالكه من البداية:

```php
// خطر: أي مستخدم مسجل يقرأ أي فاتورة
$invoice = Invoice::findOrFail($id);

// أفضل: الاستعلام نفسه لا يرى إلا فواتير المستخدم
$invoice = $request->user()->invoices()->findOrFail($id);
```

في المهارة: أول بند في الإعدادات الآمنة، وملف `references/access-control.md`.

### السؤال الرابع: ماذا لو وصل الطلب مرتين، أو عشرين مرة في اللحظة نفسها؟

الكود الذي يقول "إذا كان الكوبون غير مستخدم، استخدمه" صحيح منطقيا، وخاطئ عندما يصل عشرون طلبا معا، لأن الطلبات العشرين تمر جميعها من الشرط قبل أن يسجل أي منها الاستخدام. هذه Race Condition. والـ webhooks تصل مكررة بشكل طبيعي، لذلك كل حدث يجب أن يعالج مرة واحدة (Idempotency).

الحل دائما في قاعدة البيانات وليس في الـ if: قيد Unique، أو تحديث ذري بشرط، أو قفل صف داخل transaction.

في المهارة: ملف `references/business-logic.md`.

### السؤال الخامس: هل يمكن خداع المنطق نفسه؟

كمية سالبة تخفض السعر. خصم يطبق مرتين. طلب يقفز من "جديد" إلى "مشحون" دون "مدفوع". سعر يأتي من المتصفح. هذه أخطاء منطق الأعمال، وأدوات الفحص لا تجدها لأن الكود لا يحتوي على نمط خطير، المنطق نفسه هو الخطأ.

في المهارة: ملف `references/business-logic.md`.

### السؤال السادس: ماذا يقرأ النظام من الخارج؟

الـ payload القادم من webhook، الملف المرفوع، الصفحة التي يلخصها مساعد ذكي، البريد الذي يقرؤه وكيل. كل هذا محتوى يكتبه طرف لا تتحكم به. في ميزات الذكاء الاصطناعي تحديدا، النص الخارجي يمكن أن يحمل تعليمات للنموذج. وحسب إرشادات OWASP لتطبيقات النماذج اللغوية لا توجد طريقة موثوقة تمنع الـ Prompt Injection بالكامل، لذلك التصميم الصحيح يفترض أن النموذج سيخدع، ويضمن أنه حتى لو خدع لا يستطيع أن يسبب ضررا كبيرا.

في المهارة: ملفا `references/outbound-and-webhooks.md` و`references/ai-features.md`.

### السؤال السابع: ماذا يحدث عندما يفشل شيء؟

ماذا لو رمى فحص الصلاحيات خطأ؟ ماذا لو انتهت مهلة بوابة الدفع؟ الكود الذي يلتقط الخطأ ويكمل هو ثغرة. القاعدة: الفشل يغلق الباب ولا يفتحه (Fail Closed). وهذا بند جديد في OWASP Top 10:2025 تحت اسم Mishandling of Exceptional Conditions.

في المهارة: ملف `references/config-and-errors.md`.

## 6. لماذا يخطئ الوكلاء في الأمن تحديدا؟

فهم سبب الخطأ يساعدك على كتابة تعليمات تعالجه:

- **يحسنون للمسار السعيد.** الاختبارات التي يكتبونها تتأكد أن الميزة تعمل، ونادرا ما تتأكد أنها ترفض ما يجب رفضه.
- **يكتفون بالمصادقة.** يضيفون middleware تسجيل الدخول ويعتبرون الـ route محميا، مع أن السؤال الحقيقي هو الصلاحية على الكائن.
- **يثقون بصياغة الطلب.** إذا قال المستخدم "أرسل السعر من الواجهة" ينفذ دون أن يسأل.
- **يرون ملفا واحدا.** لا يلاحظون أن الحماية التي أضافوها في `show` غائبة عن `export` و`download`.
- **ينسخون أنماطا قديمة.** بيانات التدريب مليئة بأمثلة غير آمنة من مقالات ومنتديات قديمة.
- **يخترعون أسماء حزم.** أحيانا يقترحون حزمة باسم معقول غير موجود، والمهاجمون يسجلون هذه الأسماء وينتظرون. هذا يسمى Slopsquatting.
- **يبالغون في الطمأنة.** يختمون بجملة "الكود الآن آمن" دون دليل.

كل بند من هذه له علاج مباشر في `SKILL.md`: الاختبارات التي تفشل عند إزالة الحماية، والبحث خارج الملف في خطوة الهجوم الذاتي، وقاعدة عدم الثقة بقيم العميل، وملف التبعيات، ومنع كلمة "secure" في التقرير.

## 7. قرارات التصميم ولماذا اتخذتها

### المستويات الثلاثة

| المستوى | متى | ماذا يحدث |
|---|---|---|
| 0 | تنسيق، نصوص، توثيق، اختبارات فقط | لا شيء |
| 1 | إدخال مستخدم أو عرض بيانات دون أسطح حساسة | إعدادات آمنة بصمت، بلا تقرير |
| 2 | أي سطح حساس | سير العمل الكامل والتقرير |

السبب: المهارة التي تكتب تقريرا أمنيا عن تغيير لون زر ستحذف خلال يومين. الضجيج يعلم الناس تجاهل التحذيرات، ويحرق tokens بلا فائدة. لذلك يوجد في التقييمات اختبار مخصص يتأكد أن المهارة تصمت في المستوى 0.

### الهجمات قبل الكود

لأن كتابة "المستخدم B يغير رقم الفاتورة" قبل البناء تجعل الوكيل يختار تصميما يغلق الهجوم من الأساس. اكتشاف الخطأ بعد البناء يعني ترقيعا. والهجمات المكتوبة تتحول مباشرة إلى أسماء اختبارات.

### الاختبار الذي يفشل عند إزالة الحماية

جملة "تحققت من الصلاحيات" ليست دليلا. الاختبار الذي يسجل الدخول كمستخدم ثان ويتوقع 404 هو دليل، ويبقى في المشروع ويحمي الميزة من أي تعديل مستقبلي يكسرها. الفكرة قريبة من Mutation Testing: احذف الحماية في ذهنك، فإن لم يفشل أي اختبار فالحماية غير مثبتة.

### لا كلمة "آمن" أبدا

لأن الأمن ليس حالة يمكن إثباتها. التقرير يقول ما تم فحصه وما بقي مفتوحا. هذا أصدق، ويمنع الإحساس الزائف بالأمان، وهو أخطر من غياب الحماية لأنه يوقف البحث.

### الشرح بدل الأوامر بالأحرف الكبيرة

كل قاعدة في `SKILL.md` معها سببها في نصف سطر. النماذج الحديثة تعمم جيدا عندما تفهم السبب، وتطبق القاعدة في حالات لم يكتبها أحد. أما كلمة MUST بالأحرف الكبيرة فتجعل النموذج يطبق القاعدة بتشدد في أماكن لا تناسبها.

### ملفات مرجعية حسب المجال

ملف لكل سطح، وملف لكل إطار عمل. هكذا يقرأ الوكيل ما يحتاجه فقط، ويمكنك أن تعمق أي ملف دون أن تثقل البقية.

### دفاعية فقط

المهارة تختبر كود المستخدم في بيئته واختباراته، ولا تكتب أدوات استغلال لأنظمة الآخرين. هذا ليس قيدا شكليا. سجلات المهارات تراجع المحتوى، والمستخدمون يثقون بما يثبتونه، ومهارة تتصرف بطريقة مفاجئة تخسر الثقة فورا.

### سكربت بلا تبعيات

السكربت يعمل بمكتبة Python القياسية فقط، على Python 3.9 فما فوق. لا `pip install`، لا مشاكل في بيئات الوكلاء المعزولة، ويعمل على Windows وmacOS وLinux.

## 9. سكربت الفرز من الداخل

### صيغة الـ diff في دقيقة

الأمر `git diff` يخرج نصا بهذا الشكل:

```diff
diff --git a/app/Http/Controllers/InvoiceController.php b/app/Http/Controllers/InvoiceController.php
--- a/app/Http/Controllers/InvoiceController.php
+++ b/app/Http/Controllers/InvoiceController.php
@@ -10,3 +10,4 @@ class InvoiceController extends Controller
     public function download(int $id)
     {
-        $invoice = $request->user()->invoices()->findOrFail($id);
+        $invoice = Invoice::findOrFail($id);
```

السطر الذي يبدأ بـ `@@` يسمى hunk header. معناه: هذا المقطع يبدأ في السطر 10 من الملف القديم ويغطي 3 أسطر، ويبدأ في السطر 10 من الملف الجديد ويغطي 4 أسطر. بعده كل سطر يبدأ بعلامة: `+` مضاف، و`-` محذوف، ومسافة للسياق.

### الفخ الذي يقع فيه أغلب المحللين البسطاء

سطر كود مضاف مثل `++i` يظهر في الـ diff هكذا: `+++i`. المحلل الساذج يظنه بداية ملف جديد لأنه يبدأ بـ `+++`. السكربت يتجنب ذلك بعد الأسطر المتبقية في كل hunk من الأرقام في الـ header، ولا يقرأ أي header ما دام داخل hunk. هناك اختبار مخصص لهذه الحالة.

### وضع `--git`

الأمر `git diff` وحده لا يرى الملفات الجديدة التي لم تضف إلى git، وهذه بالضبط الملفات التي ينشئها الوكيل. لذلك الخيار `--git` يجمع الفرق مقابل `HEAD` ويضيف الملفات غير المتتبعة كأنها ملفات جديدة بالكامل.

### المراحل

1. **التحليل:** تحويل النص إلى قائمة ملفات، لكل ملف حالته وأسطره المضافة والمحذوفة مع أرقامها.
2. **التصنيف:** كل ملف يأخذ نوعا: توثيق، تنسيق، أصول، اختبارات، ملف تبعيات، CI، أو كود. التوثيق والتنسيق لا تفحص بالقواعد، لأن ملف README يذكر `exec()` في شرح ليس ثغرة.
3. **القواعد:** كل قاعدة تعبير نمطي (Regex) مرتبط بفئة، ولكل فئة مستوى وملفات مرجعية.
4. **الأسرار:** أنماط خاصة بمزودين معروفين، وفك الـ JWT لمعرفة دوره، وتجاهل القيم الوهمية، وإخفاء السر في المخرجات.
5. **الأسطر المحذوفة:** حذف `authorize` أو `throttle` أو فحص توقيع إشارة مستقلة ومهمة، حتى لو بدا الكود المضاف بريئا.
6. **المستوى:** أعلى مستوى بين النتائج. وإذا تغير كود دون أي نتيجة فالمستوى 1. وإذا لم يتغير إلا توثيق أو تنسيق أو اختبارات فالمستوى 0.

### شكل القاعدة

```python
Rule("ssrf", _rx(
    r"(\bfetch|\brequests\.\w+|\bhttpx\.\w+|Http::\w+ ...)\s*\(\s*(?=[^)'\"`\s])[^)]*\b" + URLISH + r"\w*",
    ignore_case=True,
), exclude=CLIENT_SIDE_PATH)
```

القاعدة تقول: استدعاء عميل HTTP، أول معامل فيه ليس نصا ثابتا بين علامتي تنصيص، وفي المعاملات اسم يوحي برابط مثل `url` أو `avatar` أو `webhook`. والاستثناء يتجاهل ملفات الواجهة، لأن `fetch(url)` داخل مكون React يعمل في المتصفح ولا يمكن أن يكون SSRF.

### الـ JWT: مثال على قاعدة ذكية

مفتاح Supabase العام (anon) هو JWT، ومفتاح الخدمة (service_role) هو JWT أيضا. الأول مصمم ليكون في الواجهة، والثاني يتجاوز كل سياسات RLS ويجب ألا يخرج من الخادم. السكربت يفك الجزء الأوسط من الـ JWT ويقرأ حقل `role`: يتجاهل `anon`، وينبه بقوة عند `service_role`. هذا الفرق البسيط يقلل الإنذارات الكاذبة ويلتقط أخطر خطأ في مشاريع Supabase.

### حدود السكربت

هو فرز نصي وليس تحليلا. لا يتتبع تدفق البيانات بين الملفات، ولا يفهم أن المتغير `url` جاء من إعدادات ثابتة. سيعطي إنذارات كاذبة، وسيفوت أشياء. وظيفته أن يمنع نسيان سطح كامل، وليس أن يحكم بأن شيئا آمن.

### إضافة قاعدة جديدة

1. اكتب اختبارا في `scripts/test_triage_diff.py` بـ diff صغير يجب أن يطابق، وآخر قريب منه يجب ألا يطابق.
2. شغل الاختبارات وتأكد أن الجديد يفشل.
3. أضف القاعدة، أو فئة جديدة في `CATEGORIES` مع مستواها ومراجعها.
4. شغل كل الاختبارات.

```bash
python -m unittest discover -s skills/bug-hunter/scripts -v
```

## 11. دورة تطوير المهارة

### الدورة

1. **ابدأ بفشل حقيقي.** طلب عادي جعل الوكيل يكتب ثغرة. من تجربتك، أو من تقرير منشور.
2. **اكتب حالة تقييم تعيد إنتاجه.** وتأكد أنها تفشل بدون المهارة، وإلا فالمشكلة غير موجودة.
3. **عدل أقل ما يمكن.** سطر في ملف مرجعي أفضل من فقرة في `SKILL.md`.
4. **شغل التقييمات بالمهارة وبدونها.**
5. **تأكد أن حالة الضجيج ما زالت تنجح.**
6. **سجل النتيجة في الـ commit أو الـ PR.**

### أين تضع المعرفة الجديدة؟

| المعرفة | المكان |
|---|---|
| تنطبق على كل تغيير حساس | `SKILL.md` |
| تخص سطحا واحدا | `references/<surface>.md` |
| تخص إطار عمل واحدا | `references/frameworks/<framework>.md` |
| فحص آلي يتكرر بالطريقة نفسها | `scripts/` |
| مثال على الشكل المطلوب للتقرير | `references/report-format.md` |

### الميزانية

النص `SKILL.md` يبقى تحت 500 سطر، والمستهدف أقل بكثير. الملف المرجعي الذي يتجاوز 300 سطر يحتاج قائمة محتويات في أوله. والإشارات إلى الملفات تكون بعمق مستوى واحد من `SKILL.md`، لأن الوكيل قد لا يتبع سلسلة إشارات طويلة.

### الإصدارات

رقم الإصدار في `metadata.version` يتبع Semantic Versioning: تغيير يكسر السلوك يرفع الرقم الأول، وإضافة حالات أو مراجع ترفع الثاني، والإصلاحات ترفع الثالث. اكتب ما تغير في `CHANGELOG.md` مع نتائج التقييم.

### استخدام خبرتك في مكافآت الثغرات

خبرتك هي الشيء الذي لا يملكه غيرك، وهي ما يجعل هذه المهارة مختلفة. حول كل نمط رأيته إلى سطر هجوم ودفاع واختبار. لكن بشرط صارم: لا تفاصيل من تقارير غير منشورة، ولا معلومات طلب منك برنامج ما أن تبقيها سرية، ولا أسماء أهداف. عمم النمط، وغير الأسماء، واحتفظ فقط بما هو معرفة عامة.

## 14. قاموس المصطلحات

| المصطلح | المعنى | مثال |
|---|---|---|
| IDOR / BOLA | الوصول إلى كائن شخص آخر بتغيير معرفه | تغيير `/invoices/1043` إلى `/invoices/1044` |
| BFLA | استدعاء وظيفة لا يملك المستخدم صلاحيتها | مستخدم عادي يستدعي endpoint الإدارة مباشرة |
| Mass Assignment / BOPLA | تعديل حقول محمية عبر إرسالها في الطلب | إضافة `"role":"admin"` إلى تحديث الملف الشخصي |
| SSRF | جعل الخادم يرسل طلبا إلى عنوان يختاره المهاجم | رابط صورة يشير إلى `169.254.169.254` |
| CSRF | موقع آخر يرسل طلبا باسم مستخدم مسجل | نموذج مخفي يغير البريد الإلكتروني |
| XSS | تنفيذ JavaScript في متصفح مستخدم آخر | تعليق يحتوي `<img onerror=...>` |
| SSTI | تنفيذ كود عبر محرك القوالب | إدخال `{{7*7}}` يظهر 49 |
| Path Traversal | الخروج من المجلد المسموح | اسم ملف `../../.env` |
| Open Redirect | تحويل المستخدم إلى موقع خارجي عبر رابط موثوق | `?next=//evil.example` |
| Race Condition | طلبات متزامنة تتجاوز شرطا واحدا | استخدام كوبون واحد عشر مرات |
| Idempotency | معالجة الحدث نفسه مرة واحدة مهما تكرر | webhook يصل مرتين |
| Constant-time Comparison | مقارنة لا يكشف زمنها شيئا عن القيمة | الدالة `hash_equals` |
| HMAC | توقيع رقمي بمفتاح سري مشترك | توقيع webhooks |
| RLS | سياسات على مستوى الصف في Postgres | كل مستخدم يرى صفوفه فقط في Supabase |
| Prompt Injection | نص يغير سلوك النموذج اللغوي | صفحة تقول "تجاهل تعليماتك" |
| Lethal Trifecta | بيانات خاصة مع محتوى غير موثوق مع قناة إرسال | وكيل بريد يقرأ رسائل غريبة ويستطيع الإرسال |
| Slopsquatting | تسجيل أسماء حزم يخترعها النموذج | حزمة باسم يبدو حقيقيا ولا وجود له |
| Threat Model | تحديد ما يمكن أن يسوء وماذا سنفعل | الأسئلة الأربعة |
| Abuse Case | هجوم محدد مكتوب كقصة مستخدم | "كمستخدم B أطلب فاتورة A" |
| Trust Boundary | نقطة انتقال البيانات بين مستويي ثقة | من المتصفح إلى الـ API |
| Source / Sink | مصدر القيمة والمكان الذي تصبح فيه خطيرة | من `req.query` إلى SQL |
| Fail Closed | الفشل يمنع ولا يسمح | خطأ في فحص الصلاحية يعطي 403 |
| Progressive Disclosure | تحميل المعرفة على طبقات حسب الحاجة | الوصف ثم `SKILL.md` ثم المراجع |
| Frontmatter | كتلة YAML في أول الملف | الحقلان `name` و`description` |
